# Результаты сравнения ручного и автоматизированного тестирования приложения «Хоспис»

## 1. Введение

В рамках дипломного проекта было проведено функциональное тестирование мобильного приложения «Хоспис». Тестирование выполнялось в двух подходах:

- **Ручное тестирование** – по заранее составленному чек-листу.
- **Автоматизированное тестирование** – с использованием фреймворка Espresso и Allure для формирования отчётов.

Цель сравнения – оценить эффективность автоматизации регрессионного тестирования, выявить преимущества и недостатки каждого подхода, а также зафиксировать обнаруженные дефекты.

---

## 2. Ручное тестирование

### 2.1. Данные о тестировании

| Параметр | Значение |
|----------|----------|
| Затраченное время | ~4 часов |
| Исполнитель | 1 тестировщик |
| Окружение | Эмулятор Pixel 4 API 29, Android 10 |
| Документация | Чек-лист (41 пункт) |

### 2.2. Процесс выполнения

Тестирование выполнялось вручную согласно чек-листу, который покрывал следующие функциональные области:

- Авторизация (позитивные и негативные сценарии)
- Навигация по разделам приложения
- Управление новостями (создание, редактирование, удаление, фильтрация, сортировка)
- Просмотр цитат (разворачивание/сворачивание)
- Проверка страницы «О приложении» и переход по ссылкам

### 2.3. Результаты ручного тестирования

- **Пройдено успешно:** 31 тест-кейсов
- **Выявлены дефекты:** 10 тест-кейсов (баги в приложении)

---

## 3. Автоматизированное тестирование

### 3.1. Данные о тестировании

| Параметр | Значение |
|----------|----------|
| Количество авто-тестов | 37 |
| Затраченное время | ~9 минут 30 секунд |
| Инструменты | Espresso, Allure, AllureAndroidJUnitRunner |
| Окружение | Эмулятор Pixel 4 API 29, Android 10 |
| Отчётность | Allure-отчёт |

### 3.2. Инструменты и подход

- **Espresso** – для взаимодействия с UI-элементами.
- **Allure** – для формирования детальных отчётов с группировкой по эпикам и историям.
- **Page Object Model** – для переиспользования кода и упрощения поддержки.
- **Аннотации Allure** – для упрощения навигации по классам и отчётов.

### 3.3. Результаты автоматизированного тестирования

- **Пройдено успешно:** 26 авто-тестов
- **Упало:** 11 авто-тестов (из-за дефектов приложения)
- **Время выполнения:** 9 минут 30 секунд

## 6. Заключение и выводы

### 6.1. Эффективность автоматизации

Автоматизация позволила сократить время выполнения регрессионного тестирования в **~31 раз** (с 5 часов до 9,5 минут). Это даёт возможность:

- Запускать тесты после каждого изменения кода (CI/CD).
- Быстро выявлять регрессии.
- Получать детальные отчёты (Allure) с шагами, скриншотами и логами.

### 6.2. Итоговый вывод

Автоматизированное тестирование является **объективно более эффективным** для регрессионных проверок, однако требует дополнительных затрат на разработку и поддержку авто-тестов. В долгосрочной перспективе инвестиции в автоматизацию окупаются за счёт экономии времени и повышения качества продукта.

Рекомендуется продолжать развитие автоматизации и параллельно вести ручное тестирование для проверки новых функций на ранних этапах разработки.
